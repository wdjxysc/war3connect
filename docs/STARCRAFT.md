# 星际争霸：母巢之战 1.16.1 — 第一阶段

当前只提供游戏识别、启动和平台准备房间，**尚不能通过平台跨网络对战**。

## 已实现

- 客户端选择星际后，独立保存 StarCraft.exe 路径、Wine 程序与 WINEPREFIX；原有 War3 设置自动迁移。
- 从 PE 版本资源读取完整版本号，只接受 1.16.1.x；房间成员必须使用相同完整版本。
- 星际启动不会附带 War3 的 `-window` 参数。Linux 仍通过 Wine 启动，实际游戏兼容性待验证。
- 房间以 `starcraft-bw` 标识，与 `war3-tft` 隔离，最多 8 名平台成员。
- 准备房间提供成员、聊天、心跳和清理；不发布 War3 公告、不建立 War3 TCP 代理。
- 协议版本升级为 3，客户端与服务端需同步升级；没有自动更新远程部署。

## 验证范围

自动测试覆盖合成 PE 资源版本识别、启动参数、跨游戏隔离、人数限制、HTTP 房间与聊天、准备房间代理状态，以及原有 War3 模拟端到端转发。
这些检查不代表真实 StarCraft.exe 已启动或已完成对局。

## 下一阶段：实际游戏与网络验证

1. 提供合法安装的 StarCraft.exe 路径并确认母巢之战数据完整。
2. 两台 Windows 设备以相同 1.16.1 完整版本验证 Multiplayer → LAN (UDP) 的原生发现、入房和开局；增加第三名玩家确认玩家之间的通信。
3. 验证房间虚拟网络的广播发现与双向数据传输，再选定集成方案。仅提供虚拟 IP 不能保证游戏列表可见。
4. 接入隧道认证、房间隔离、退出清理和诊断信息；验证地图传输、完整对局、丢包和断线表现。
5. 在 Windows 验收后验证 Linux/Wine。

## 主动查询与 UDP 代理实验（尚未完成游戏接入）

当前优先验证不安装驱动、不创建虚拟网卡的路线。

- 已实现主动查询探测器，向目标 UDP 6111 发三次查询，默认绑定随机源端口。
- 查询样本来自 [tingar/udp-proxy 的协议记录](https://github.com/tingar/udp-proxy/blob/dab2165089e0d3e5f65d1790484a2f0c4279bb7d/protocol.asciidoc)，字节为 `D9FA14000200000050584553D300000000000000`。参考发送程序使用固定源端口；尚未证明这个样本可通过随机端口查询实际 1.16.1。
- 界面选择星际后可点击“实验：探测本机星际主机”，先在游戏 LAN（UDP）中建图并停留房间；结果写入连接日志。
- 也可构建后运行 `./scripts/probe-starcraft.ps1`；报告保存在忽略的 `artifacts/starcraft-probes/`。报告含本地地址和原始游戏数据，仅用于私有诊断。
- 从第二台电脑探测时使用 `-TargetAddress <房主局域网IPv4>`；可用 `-SourcePort 6111` 对比固定端口，仅在该端口未被游戏占用的设备测试。不会启用端口共享或抢占游戏端口。
- 只收集来自目标 IP 和端口的单播回复；发往其他端口、其他网卡或广播地址的回复可能收不到。超时不证明游戏没有主机，也不证明必须用驱动。
- “历史公告头匹配”仅检查长度、类型、产品字节和记录中的版本字段，不验证校验和，不代表完整有效的游戏公告。

另外已实现独立 `UdpSocketBridge`：每个二进制 WebSocket 消息对应一个 UDP 数据报，支持分片重组、空数据报，限制固定本机端点，拒绝其他发送者及超长/文本消息。它只是单个对端的传输组件，**尚未接到星际房间**。现有服务端中继按字节流工作，不能直接假定其保留 UDP 消息边界；还需实现端到端数据报封装、成员间寻址、房间生命周期和公告接入。WebSocket 基于 TCP，丢包时会产生等待，不能把它等同于原生 UDP 的时延表现。

下一次实机验证要回答：本机单播查询是否接受、回复目的端口是否跟随源端口、公告重发是否可见、加入过程是否在载荷中交换地址。回答这些问题后再接通房间代理，避免只显示主机却无法加入。

参考：[StarCraft Over VPN 作者说明](https://s-softs.com/Projects/SoV/index.html)记录了星际 UDP 广播发现跨 VPN 的问题。它只用于方案研究，本项目未引入其源码、旧版驱动或二进制文件。
